# Keyboard in the stock Tidal > Search page

**Sources:** `patch/tidalkb.c` (`tidal_kb_focus`), `patch/tidalkb.h` (the field's geometry); `tools/pod_ui.py` `add_tidal_keyboard` (the asset edit, called by `tools/pod.py`); `tools/pod.py` `TIDALKB_SITE`, `TIDALKB_SEARCH`, `TIDALKB_PINS`; test `test/pod/tidalkb.py` (sections `hook_tests`, `asset_tests`, `life_tests`, `history_tests`, `research_tests`, `navbtn_tests`, `order_tests`, `fallback_tests`, `destroy_tests`); preview `tools/preview_tidalkb.py`. The keyboard itself is [keyboard](keyboard.md) (`keyboard_attach`); nothing new in it.

Stock's Tidal > Search page (`tidal/tidal_serach_page`, init `tidal_tidal_serach_page_init` `0x4c4a24`, asset `ui/tidal/tidal_serach_page.bin`) has one edit, `search_edit` (`password_visible` true, max 127), and is the only text entry of the Tidal screens (the login is a device-code flow). It opened stock's T9 popup (`kb_default_t9`); it now shows our pad **inside the page**: Tidal's toolbar and search bar stay as they are, the pad sits at the bottom of the window over the history / results, and what is typed shows in the bar. No page of ours opens (the first build opened the keyboard page with its own navbar; the device report: "too abrupt ... even the toolbar style is different").

## Stock side (disassembly)

- The page init walks its widgets with a callback (`0x4c1f3c`; `s0` = the widget, `s1` = the window). For the widget named `search_edit` it calls `edit_set_focus(edit, 1)` at **`0x4c2088`** (`lw t9` GOT @`0x4c2080`, `a1 = 1` @`0x4c2084`, delay slot `move a0, s0` @`0x4c208c`), then binds the IM action event `0x13c` of the edit to `0x4c4990` (ctx = the window) and sets the tips from `getFormatString("search_tips1")` (stock English "Search for music,artists,albums"; de, es and pl have no such key; the page keeps setting it on the hidden edit, our bar shows `Search Tidal` instead). The callback names every widget it cares about by strcmp; our added `kb_*` widgets match none.
- `edit_set_focus` (`0x62a1dc`) = `widget_set_focused` (the EVT_FOCUS event reaches `edit_on_event`, whose focus case calls `input_method_request`, which pops T9) and a state update. The hook does not call it, so nothing asks the input method.
- The search routine `0x4c4740(w, event)` uses only `w`: `widget_get_window(w)`, `widget_lookup(win, "search_edit")`, `widget_get_text_utf8` into `0xa0eac8`, the 5 entry history (`0xa0ed58`, 256 bytes each, newest first) written to `/mnt/data/tidalhistory` (always, also for an empty text), then, for a non-empty text, `0x4c2254(win, 1)` (waiting state), `navigator_close("kb_default_t9")` (harmless when T9 is not open) and `0x4c2380(win)` (the search); for an empty text the `msginfo_dialog` warning `keyboard_keyword`. The event argument is never read.
- `0x4c2254(win, state)` looks up `view` (the history list, y 50), `tab_control` (the results, y 50) and `search_edit`: `view` visible = `!state`, `tab_control` visible = `state`, and for state 1 the keyword buffer `0xa0eac8` is written into the edit. A **tap on a history row** (the row's click `0x4c2e10`: the label text of `label_record_N` into `0xa0eac8`, `bal 0x4c2254` @`0x4c2edc`, then the search) therefore changes the edit's text without our knowing.
- `widget_dispatch` (`0x66cec8`) runs the widget's on_event (vtable slot `0x94`) when there is one and then the emitter (user handlers, `widget_on`) unless on_event answered `RET_STOP` (`0xb`, `0x66cf4c`). A `view` has no on_event (slot `0x94` of its vtable at `0x97b2d8` is NULL), so the touch goes on to its parent. Pinned in `TIDALKB_PINS`, checked against the stock binary by `hook_tests`.

## The asset

`add_tidal_keyboard` (build time, `modlib.edit_ui`; asserts the stock layout) adds to `ui/tidal/tidal_serach_page.bin` (the only copy in the rootfs; no theme variants):

- inside the bar's `list_item` `listitem_ssid` (33, 6, 240 x 38, `search_bg` pill), after the stock `search_edit` (15, 0, 210 x 38): **`kb_field`** (x `TK_FIELD_X` 19, 206 x 38, transparent, sensitive) with `kb_hint` (the stock tips colour `#AAAAAA`; text `Search Tidal`, 13 translations in `tools/pod_i18n.py`, widest 135 px (fr, de) in the 166 px `TK_TEXT_W`: `asset_tests`), `kb_text` (white), `kb_caret` (2 x 22 at y `TK_CARET_Y` 8) and `kb_clear` (36 px wide at the field's right end, hidden and insensitive), font size 18 = the stock edit's. The text room is `TK_TEXT_W` 166 (up to the clear button); a longer text shows its end after an ellipsis, as everywhere. There is no magnifier (the stock bar has none). The stock `search_edit` stays in the tree (stock's routines look it up) but is hidden and insensitive at run time.
- at the end of the window (so painted over `view`, `tab_control` and the wait image): `keyboard_pad_widgets()` (`kb_pad`, `kb_strip`, `kb_stem`, `kb_pop`), byte for byte the keyboard page's. The window is the 450 px client area (`view` 50 + 400), the same as the keyboard page, so the pad's bottom (270 + 180) is the screen's bottom. The pad starts below the toolbar and the bar; the Chinese candidate strip (y 234) covers the history only.

Without the edit (an unedited asset) `keyboard_attach` finds no `kb_pad`: stock's T9. `asset_tests` also compares the edited page with stock's: taking our widgets out gives the stock bytes.

## The tap (device report V2.1zRGSRAAAC: the first build bound EVT_CLICK on the edit, and a tap on the bar after a search did nothing)

AWTK's `edit` never emits `EVT_CLICK`; the widget that turns a tap into `EVT_CLICK` is the bar's `list_item`:

1. The window manager calls `widget_on_pointer_down` (`0x67126c`) / `widget_on_pointer_up` (`0x67187c`) on the window. Each level emits the raw pointer event to its own emitter, asks `widget_find_target` (`0x666bdc` -> `0x6747d4`; a grabbed child `0x4c(widget)` wins, else the topmost child under the finger with flags & 9 == 9, so `kb_field`, not the hidden edit) and recurses into the child. Only when the child did not answer `RET_STOP` (`0xb`; `0x67133c`, `0x67199c`) the parent's `widget_dispatch` runs (`0x67134c`; up: `0x66e224`).
2. `kb_field` is a `view`: no on_event, so it answers `RET_OK` and the event goes on to `listitem_ssid`. (The clear button is a button: it takes its own touch.)
3. `list_item_on_event` (`0x60bb80`): on pointer down it sets pressed (`0x7e`) and the `0x7d` flag, remembers x / y, `widget_grab`s itself, arms a 30 ms timer. On pointer move it sets the dragged flag (`0x7c`) when the y moved 11 px or more and ungrabs. On pointer up a click is sent only if not dragged (`0x60bd58`) and pressed (`0x60bd68`): `event_init(type 0x10c = EVT_CLICK)` (`0x60bd8c`) and `widget_dispatch(list_item, ...)` (`0x60bdcc`), which runs the handlers bound with `widget_on(list_item, EVT_CLICK)`. The click is on the **list_item**.
4. The hook binds `EVT_CLICK` on the edit's parent (`*(edit + W_PARENT)`; the edit itself when it has no parent but the window), with the edit as context. A drag that starts on the bar is no click.
5. After a search `0x4c2254` / `0x4c2380` only touch `view`, `tab_control`, `image_wait` and the edit's text; `listitem_ssid` and `kb_field` are never rebuilt, so the same handler takes the tap with the results showing.

Tests model this chain (`tap()` in `test/pod/tidalkb.py`): raw pointer events to `kb_field`, `EVT_CLICK` to the bar only, none on a drag, also after a search. The chain is read from the disassembly and pinned; the real `list_item_on_event` is not run in the emulation.

## Design (payload hook 27)

One call-site hook ([payload](payload.md) hook 27): the `jalr edit_set_focus` at `0x4c2088` is `jal tidal_kb_focus`. The result is unused by stock. Everything is decided once, in the page's init, before anything is changed.

1. `tidal_kb_focus(edit, 1)` with no keyboard already up (`keyboard_busy()`), an edit in a window: `keyboard_attach(win, hint, TK_TEXT_X, TK_TEXT_W, TK_CARET_Y, 0, tk_on_change, tk_on_go)` (the hint is `TR("Search Tidal")` in every language), binds the page's `EVT_DESTROY` and the bar's `EVT_CLICK`, arms the 250 ms poll, hides and disables the stock edit and returns without focusing it. Attaching inside the init is fine: `keyboard_attach` only looks widgets up by name and sets their properties, needing neither the window stack nor the page on top (the Search and Radio pages do the same in their init). Anything else (a keyboard up, no window, no `kb_pad` etc. in the asset, a handler that will not bind - the keyboard is detached again) runs stock's `edit_set_focus(edit, 1)` unchanged: T9 as before.
2. Typing: `tk_on_change(text)` writes the committed text into the stock edit on every change (the search routine reads only the edit; its limit is 127 bytes, and the field takes as many: `keyboard_set_max(TK_MAX)` after the attach). The bar shows the pad's own field widgets.
3. The action key (`tk_on_go`): the text without spaces at both ends (an empty one does nothing and the pad stays) goes to the bar (`keyboard_set_text`, so the edit too), then `keyboard_show(0)` and stock's `0x4c4740(edit, 0)` (history file, waiting state, search; the results show where the pad was). The bar keeps the text and has no caret.
4. A tap on the bar (`tk_on_click`) with the pad hidden: `tk_sync` and `keyboard_show(1)`; with the pad up nothing.
5. **History taps**: stock writes the row's text into the edit (see "Stock side"). The poll (`tk_tick`, 250 ms, re-armed by its own callback, page-scoped) compares the edit's text with the pad's; a difference means stock put it there: `keyboard_set_text` (cut to 127 bytes) shows it in the bar and `keyboard_show(0)` lets the results show. A tap on the bar syncs first too, so a missing timer only delays this to the next tap. While typing the two are always equal (`on_change` is synchronous).
6. The page's destroy (`ctx == tk.win`) removes the poll and calls `keyboard_detach`; a second Tidal search page while the first still has the keyboard gets stock's T9 (one keyboard at a time).

7. **The navbar Search button.** Stock's page init (`0x4c4a24`) creates a button in `navigationbar_view` before the `widget_foreach` that runs the hook: `button_create(nav, 0x111, 0, 0x2f, 0x32)` (x 273, y 0, 47 x 50; `0x4c4a74..0x4c4a8c`), style `search_style`, and `widget_on(button, 0x10c, 0x4c4740, win)` (`0x4c4aac..0x4c4ac8`); nothing else is added to the navbar before the hook, so the button is the navbar's last child. Left alone, a tap on it ran stock's search directly: the pad stayed over the results and `tk_reset_results` was skipped (results appended behind the old ones). AWTK's emitter runs the newest handler first and `RET_STOP` ends the dispatch (`emitter_on_with_tag` puts a handler at the head `0x6f466c` / `0x6f4670`, `emitter_dispatch` `0x6f450c`; [playmore](playmore.md)), so the hook binds `tk_on_search_btn` (ctx = the window) on that button: `tk_sync`, then the action key's own path, `keyboard_go` (patch/keyboard.c: `kb_finish`, which commits a pending pinyin composition as its first candidate before `on_go`, so `nihao` typed without a candidate picked searches 你好 and a committed prefix is not searched alone), which runs `tk_on_go` (trim, hide the pad, reset the results, stock's search; an empty text does nothing), and answers `RET_STOP`, so stock's handler does not also run. The button is found by `tk_search_btn` (last child of the navbar, geometry 273 / 0 / 47 / 50 or none); a missing button or a failed bind is a fallback like the others. After the page's destroy the handler passes the tap on (`RET_OK`). Pins in `TIDALKB_PINS`; test `navbtn_tests` delivers the tap through a mock emitter that keeps the handlers newest first (stock's handler bound first, as the page init does) and stops at `RET_STOP`; its Chinese cases run demo's real pinyin engine (pending `nihao`, and `Wo` + pending `nihao`).

**Fallback cleanup.** The asset starts `kb_pad` visible and `kb_field` sensitive, so every path that returns to stock's T9 (a keyboard up, no `kb_pad` etc., a missing navbar button, a handler that will not bind) hides both and makes them insensitive (`tk_hide_ours(win)`, looked up by name; no window: nothing to hide). Otherwise the unbound pad would cover the bottom 180 px and the field would take taps meant for the stock edit. Test `fallback_tests` checks it on each path.

No fallback state is needed after the init: nothing of the embedded path can fail later (no kill-switch check: a tap-only hook on a stock page relies on its stock fallback). Pinyin and the other keyboard features come from the shared keyboard (Settings > Keyboards). Not at boot, no new import or thread; stock functions called by address: `edit_set_focus`, `widget_get_window` (`FUNCTIONS`) and `0x4c4740` as `stock_tidal_search`.

## Re-search (device report: search "a", tap the bar, type "b", Search: the results did not refresh)

Stock never clears the previous results in the search routine; the tab buttons do it before they search, and the page init once (`0x4c4b4c..0x4c4b94`), which is why only the first search worked:

- The search threads (`tidalSearchTracksThd` `0x51f164`, artists `0x52061c`, albums `0x51f338`) only download to `/tmp/tidal_<tid>` (no deque calls) and set the flag byte `0xa06320` = 2. The page's 500 ms timer `0x4c3bb4` sees it and runs `0x4c3238`, which parses the file (`parseTidalSearchTracksJson` `0x51fb34` sets `total` / `limit` and `_deque_push_back`s onto `*(0xa10264 + 0xc)`; the tab word `0xa04158` selects tracks / artists / albums) and rebuilds the list from the whole deque, so new rows were appended behind the old ones. Everything on the deques runs on the UI thread (the parse in the timer, the tab buttons, our `tk_on_go`), so clearing there is safe even with an earlier thread still downloading (its answer is parsed later, into the cleared deque, like a tab tap during a search).
- `0x4c2380` picks the struct by `0xa04158`: 0 tracks `0xa10264` (thread `0x51f164`), 1 artists `0xa10254` (`0x52061c`), 2 albums `0xa10244` (`0x51f338`); the struct is `{ total, limit (+4), offset (+8), deque_t * (+0xc) }`, the offset is the thread's argument. The timer restores the scroll offset `0xa04150` (`0x4c3c70`).
- The tab buttons (`btn_track` `0x4c2854`, `btn_artist` `0x4c27c0`, `btn_album` `0x4c272c`) set the tab word and, when the keyword `0xa0eac8` is not empty: limit `0x32`, `deque_clear(*(s + 0xc))`, offset 0, and in the delay slot of `bal 0x4c2380` `0xa04150 = 0`.

`tk_on_go` (`tk_reset_results`) does the same before `0x4c4740`: limit 50, offset 0, `deque_clear`, scroll 0, for **all three** structs (the current tab is not changed). The current tab's struct is the one searched; the others are cleared too because a tab tap clears and searches its own again anyway, and stale rows of another query never show. `total` is left to the parse, as the tab buttons leave it. The pins are in `TIDALKB_PINS`; the stock addresses are `DATA` `TIDAL_TRACKS` / `TIDAL_ARTISTS` / `TIDAL_ALBUMS` / `TIDAL_SCROLL` (`0xa04158` is only pinned). Test `research_tests` seeds the three deques, runs a second search through the pad and checks the state at the moment stock's `0x4c2380` is entered (the thread and parse are not run).
